# 仓库拣货示范工程

C 触屏拣货 + Web 调度 + 后台 API + SQLite 的可运行示范。覆盖：订单拆到多台设备、
可过期租约、扫码实绩幂等、离线短批、部分短缺、实物待核对、地图版本锁定与图文一致、
完成条件门控。

## 运行

```bash
npm install            # 已含 express、better-sqlite3（v11 预编译）
npm start              # http://localhost:3000
npm test               # 38 项验收断言（需先 npm start）
```

- 首页 <http://localhost:3000/> 导航到三个端
- `GET /c.html` C 触屏（设备号默认 CART-07，可改）
- `GET /dispatch.html` Web 调度端（拆单/租约/地图发布）
- `GET /admin.html` 管理页（计划/已拣/已核对差异、核对、撤销、完成）
- 删除 `db/pick.db*` 可恢复种子数据；租约时长由环境变量 `LEASE_MS` 调整（默认 120 秒）

## 关键设计

### 1. 库存两本账：占用 vs 实物

`inventory(on_hand, available)`，`available = on_hand − 已占用`。

- **分配任务**：`available -= qty_alloc`（占用）。同一订单行多次分配，累计不超计划；可用量不足整单回滚。
- **扫码确认**：实物离架，`on_hand -= qty`；占用早已建立，**available 不再动**。
  （若扫码再扣 available 会双重扣减，把自己占用的货判成"无货"。）
- **部分短缺上报**：找不到的部分解除占用 `available += missing`，`on_hand` 不动，留给盘点调账。
- **撤销一条错扫**：实物回架 `on_hand += qty`；任务行还在，占用保留，available 不动。

所有判断+扣减+写实绩在同一事务，SQL 带 `WHERE available>=? / on_hand>=?` 兜底并发。

### 2. 可过期租约：到期不抹实物

`pick_task(device_id, lease_until, lease_epoch)`。

- 领取/续租写新的 `lease_until`；调度"调走"令 `lease_epoch+1`、设备清空、任务回池。
- **每条实绩记录 `lease_epoch` 与结果**，租约失效只影响"以后还能不能在该租约下扫"，
  从不删除或回滚已 `accepted` 的行。
- 任务被调走后旧设备"最后一扫"到达：
  - 本行仍有未拣额度且实物账够 → `late_kept`：**实物保留**，状态直接进"实物待核对"，写 `late_scan` 异常；
  - 已被新租约拣满 → `late_rejected`：提示物料放异常区，不入库不占账。

### 3. 逐扫确认 vs 本地短批

| | 逐扫确认 | 本地短批 |
|---|---|---|
| 在线时 | 每扫一次请求，服务端即时判超拣、即时扣实物账 | 也可手动切到该模式攒批 |
| 离线时 | 扫不出去，失败的扫自动落入本地队列（不丢） | 本地按"分配量"计数封顶，先拦一道超拣 |
| 恢复成本 | **逐条粒度**：成功/失败互相独立，重放时哪条有位算哪条，冲突面是"这一件" | **整批粒度**：服务端在一个事务里复核全批，任一行超分配/实物不足 → **整批原子回滚**，需人工逐件核对后拆分重提 |
| 幂等 | 每条 `client_uid` 唯一索引，连发/重传只返回首次结果 | `batch_id` + 每条 `client_uid` 双幂等，重复上传不会二次扣账 |

**离线防超拣的边界**（已在界面明示）：终端离线时只能看到自己任务行的分配量与本地累计，
看不到其他设备此刻的占用，因此本地封顶是"第一道闸"；真正的跨设备可用量裁决在恢复提交时由
服务端事务完成。短批整批拒绝正是把这道差异显式暴露给人工，而不是悄悄部分入库造成账实不符。

### 4. 实物待核对状态（picked → verified / revoked）

扫码成功只代表"系统记录已拣"，实物在料箱里尚未复核：

```
accepted / late_kept ──► picked（实物待核对）──管理页实物核对──► verified
                                   │
                                   └──撤销(必须引用原实绩 uid)──► revoked
```

- 管理页三列数量：**计划 / 已拣(系统) / 已核对(实物)**，差异 = 已拣 − 计划；
  `待核对 = 已拣 − 已核对`。
- 撤销不可删流水，而是写 `revoke_voucher` 并引用原 `client_uid`；
  唯一约束保证一条实绩只能撤一次，重复提交不会再次回补账目。
- 已核对记录不能直接撤销，强制走差异处理流程。

### 5. 地图版本：旧任务永远按它用过的版本展示

- `task_line.map_version` 在分配时快照当前 active 版本，此后与地图解耦。
- 布局更新产生 draft 新版本；发布时：
  1. 用相邻货架坐标**重算箭头角度**，与库内 `arrow_dir` 比对，任何不一致拒绝发布；
  2. 校验坐标范围；通过后旧 active 置 retired、新版本 active。
- C 端打开任务先按 `map_version` 拉整张地图，**货架文字、坐标、箭头取自同一版本同一响应**，
  渲染上不存在"文字来自新版、箭头来自旧版"的拼接路径。验收中同一货架 v1 箭头 180°、v2 为 51°。

### 6. "文字正确而箭头错误"不得投入执行

- 箭头不是手画图层，而是由坐标+动线 seq 在发布时计算的快照数据；服务端发布前再校验一次。
- 底图加载失败（404/网络）时 C 端显示斜纹阻断层，`bgReady=false`，**扫码入口直接拒绝开工**，
  只能"重新加载底图"或报修——防止操作员在没有方位参照时凭文字猜货位。

### 7. 完成按钮的业务门控

`/api/tasks/:id/progress` 返回 `canComplete` 与 `gateReasons`，按钮前端置灰，服务端
`/complete` 再次强校验：

- 每行实物全部核对（待核对=0）；
- 已拣 ≥ 计划，**或** 存在已闭环的短缺异常（业务接受差异）；
- 无未处理短缺异常。

## 验收场景对应（`npm test`）

1. 扫描枪连发 5 扫：恰按分配量 accepted，其余 overpick；
2. 同一 `client_uid` 重传三次：只扣一次实物账；
3. 任务被调走后最后一扫：原实绩保留，迟到扫 `late_kept` 待核对；
4. 部分短缺：占用回补、异常闭环后才允许完成；
5. 终端断电：本地短批恢复提交，重传幂等；
6. 离线短批超拣：整批 `BATCH_OVERPICK` 原子回滚；
7. 撤销引用原实绩，重复撤销/伪造引用被拒；
8. 发布 v2 后，旧任务仍按 v1 坐标与箭头展示；
9. 底图 404：接口确为 404，前端阻断开工；
10. 逐扫的逐条成败语义（与短批恢复成本对照）；
11. 未核对点完成被拒，核对后放行；
12. 扫错货架拒绝并写异常。

## 已知简化（示范工程）

- 条码用文本输入模拟：`A-0x` 或 `SHELF:A-0x` 视为货架码，其余视为 SKU 码。
- 断网通过页面按钮模拟（离线时根本不发请求），真实部署换成拦截 fetch/网络状态即可。
- 一台演示机用设备号区分；心跳 15 秒一拍。
